# CSS 3D, measured twice — what it costs and what actually blocks it

**Date** 2026-09-04. A spike, run because the owner asked for 3D where 3D
explains better, and because `VOCABULARY.md` Gap 2 estimated CSS-3D depth at two
to three weeks without saying what the two to three weeks are *for*. They are
not for the CSS. Both measurements below were taken on the demo deck; the spike
itself was deleted.

## 1. Determinism: 3D costs byte-identity, and nothing else

A CSS 3D transform on an element with no text inside it —
`#s11-f img { transform: rotateY(16deg) rotateX(6deg) }`, the claim-figure
plate — built PASS and then drifted:

```
2953 of 3120 frames byte-identical, 167 differing,
worst 83.90 dB at frame 1905 of 3120 — above the 40 dB floor
PASS — 0 error(s), 0 warning(s)
```

The same deck without the transform is **3120 of 3120 byte-identical**.

So 5.4% of frames differ between two renders at different worker counts, by an
amount 44 dB clear of the floor — invisible, and well inside what `drift` calls
stable. What is lost is not correctness but the *byte-identical* claim, which
`drift --identical` rests on.

**That is a smaller loss than it sounds**, and the README already says why:
`--identical` is "only honest for an image-free deck with no camera". Any deck
that carries a figure or a camera dive is already judged by the PSNR floor. A 3D
archetype would cost byte-identity only for decks that had it — the plain
fixture — and those are exactly the decks that would not use a 3D archetype.

**Determinism is therefore not the blocker.** Pin `--workers 1` if a deck needs
byte-identity back.

## 2. Layout: this is what the two to three weeks are for

Rotating an existing diagram is not a CSS change. A 14° `rotateX` on `stack`'s
own SVG — nothing else touched — turned the build red:

```
error  overprint  svg_text_overprint  #s6 draws chart labels on top of
each other: 4 overlapping pair(s) at t=45.92s — "Dense carrier" over
"token count preserved", "Dense queries" over "one per position",
"Synchronisation" over "neuron-level history"
```

Every archetype here solves its layout in flat reference space and places text
at gaps it has measured. Perspective compresses vertical distance
non-uniformly, so labels that were 40px apart are not, and the further from the
vanishing point the worse it gets. The gate caught it — `svg_text_overprint`
exists because `hyperframes check` exempts SVG text from `content_overlap` —
which is the gate working, not a bug.

A 3D archetype has to be **laid out after the projection, not before**: solve
where the text lands in screen space, then place it. That is a second layout
solver living beside the flat one, per archetype that wants depth. It is real
work, and it is the work — not the transform, not the determinism story.

## What this means for the next person

- Do NOT retrofit `transform: rotate3d(...)` onto an existing archetype. It
  builds red, and if the labels happened not to collide it would build green and
  be wrong at a different beat.
- A purpose-built 3D archetype is viable on every axis this project usually
  worries about: it passes `drift`, the gates still see its DOM text, the type
  floor still measures declared sizes.
- Its cost is one screen-space layout solver, and its price is byte-identity on
  decks that would otherwise have it.
- three.js remains a separate and much larger question — no WebGL in the capture
  browser without ANGLE flags two code paths do not pass, one `<canvas>`
  disables static-frame dedup for the whole render, 16 contexts maximum, and
  every gate blind inside the canvas. Nothing here changes that.
